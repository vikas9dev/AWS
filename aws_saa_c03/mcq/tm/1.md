**A company uses Amazon EC2 instances, Amazon RDS, and Amazon S3 to run its application. During a recent review of its infrastructure costs, the company noticed unusual spending patterns.
The company wants to monitor usage costs and send alerts to the appropriate departments when there is unusual spending from its workload.
Which option will meet these requirements?**

**Options:**

- Create a zero spend budget template in AWS Budgets
- In the AWS Billing and Cost Management console, create a cost monitor using AWS Cost Anomaly Detection
- Use AWS Cost Explorer and enable multi-year data at monthly granularity
- Enable Amazon CloudWatch to monitor costs and detect unusual spending

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer

**In the AWS Billing and Cost Management console, create a cost monitor using AWS Cost Anomaly Detection**

**Hint:** The key requirement is **automatic detection of unusual spending and alerting**, not just reporting or visualization.

### 🧠 Why this is correct

- **AWS Cost Anomaly Detection** uses **machine learning** to identify **unexpected cost spikes**
- Automatically analyzes spending patterns across:

  - EC2
  - RDS
  - S3

- Sends **alerts via Amazon SNS or email** when anomalies are detected
- Does **not require predefined thresholds**, unlike budgets
- Designed specifically for **unusual or unexpected cost behavior**

This directly satisfies:

- Monitoring usage costs ✅
- Detecting unusual spending ✅
- Sending alerts to teams automatically ✅

### ❌ Why the other options are incorrect

- <span style="color:red"><strong>Create a zero spend budget template in AWS Budgets – Incorrect</strong></span>
  Budgets require **static thresholds**. A zero-spend budget is impractical and does not intelligently detect anomalies.

- <span style="color:red"><strong>Use AWS Cost Explorer with multi-year data – Incorrect</strong></span>
  Cost Explorer is for **analysis and visualization**, not real-time monitoring or alerting on anomalies.

- <span style="color:red"><strong>Enable Amazon CloudWatch to monitor costs – Incorrect</strong></span>
  CloudWatch monitors **resource metrics**, not **billing and cost anomalies**.

### 🧠 Summary

- **AWS Cost Anomaly Detection** → ML-based anomaly detection + alerts ✅
- **AWS Budgets** → Threshold-based alerts only ❌
- **Cost Explorer** → Reporting tool ❌
- **CloudWatch** → Resource monitoring, not billing ❌

</details>

**A company needs to limit the visibility and discoverability of workloads across AWS accounts with differing administrative requirements. Using AWS Organizations, accounts are grouped into organizational units (OUs).
A solution is required to monitor changes to the OU hierarchy and allow stakeholders to subscribe to related alerts.
Which option meets these requirements with the LEAST administrative overhead?**

**Options:**

* Use AWS CloudFormation stacksets to create resources across Organizations. Initiate the drift detection operation on a stack to identify changes
* Use AWS Service Catalog to create accounts in Organizations. Configure an AWS CloudTrail organization trail to consolidate changes across accounts
* Use AWS Control Tower to provision the AWS accounts. Enable account drift notifications
* Use AWS Control Tower to provision the AWS accounts. Set up AWS Config aggregated rules

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer

**Use AWS Control Tower to provision the AWS accounts. Enable account drift notifications**

**Note:** The key phrases are **“monitor changes to the OU hierarchy”**, **“subscribe to alerts”**, and **“least administrative overhead.”**

### 🧠 Why this is correct

* **AWS Control Tower** is purpose-built for **governing multi-account environments** using AWS Organizations
* It **natively monitors** changes (drift) in:

  * Account baselines
  * OU placement
  * Guardrails and governance configurations
* **Account drift notifications** automatically alert stakeholders when:

  * Accounts move between OUs
  * Governance baselines are modified
* This requires **minimal setup** compared to stitching together multiple services

Control Tower provides **out-of-the-box monitoring and alerting** with the lowest operational burden.

### ❌ Why the other options are incorrect

* <span style="color:red"><strong>AWS CloudFormation StackSets + drift detection – Incorrect</strong></span>
  Drift detection only applies to **CloudFormation-managed resources**, not OU hierarchy changes, and requires manual execution.

* <span style="color:red"><strong>AWS Service Catalog + CloudTrail – Incorrect</strong></span>
  While CloudTrail can log changes, it does **not provide simple subscription-based alerts** for OU hierarchy changes and requires additional tooling.

* <span style="color:red"><strong>AWS Control Tower + AWS Config aggregated rules – Incorrect</strong></span>
  AWS Config aggregated rules add **extra configuration and management overhead** and are not needed when Control Tower already provides native drift detection.

### 🧠 Summary

* **AWS Control Tower drift notifications** → Native OU monitoring + alerts with minimal effort ✅
* **CloudFormation / CloudTrail / AWS Config** → Higher setup and operational overhead ❌

</details>
